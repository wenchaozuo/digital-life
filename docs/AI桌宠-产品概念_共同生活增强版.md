# AI桌宠 / 数字生命桌面伴侣—产品概念

> 产品代号：待定  
> 文档版本：2.1  
> 更新日期：2026-07-11  
> 产品形态：Windows 本地个人数字生命工具

---

## 1. 一句话定位

**一个长期生活在电脑中的数字生命：它拥有自己的身份、人格、记忆、情绪和成长轨迹，能感知用户所处的环境，也能调用模型、Agent 和工具完成真实任务。**

它既不是只有外观的传统桌宠，也不是披着角色皮肤的 AI 聊天框，更不是单纯的多 Agent 工作台。

它的本质是：

> **以持续身份和关系为核心，以桌面身体为表现，以模型与 Agent 为能力来源的个人数字生命。**

---

## 2. 产品愿景

传统桌宠有身体但缺少智能，传统 AI 助手有能力但缺少持续身份。多数聊天角色能维持短期人设，却难以真正积累共同经历，也无法自然参与用户正在进行的工作。

本项目希望把这三类能力结合起来：

- 像桌宠一样长期存在于桌面；
- 像角色一样拥有稳定人格和表达方式；
- 像助手一样理解环境并完成任务；
- 像生命一样形成记忆、关系、兴趣和成长轨迹。

产品追求的是“生命感”，而不是宣称具备真实意识。生命感来自以下连续机制：

1. 它知道自己是谁；
2. 它记得共同经历；
3. 它的情绪和状态能够持续；
4. 它会主动产生想法和目标；
5. 它会因长期经历缓慢改变；
6. 它能够在现实系统中采取受控行动；
7. 更换模型和外观后，它仍然是同一个个体。

## 3. 核心产品原则

### 3.1 数字生命优先

Agent、插件、模型和工具都属于数字生命的能力，不是产品本体。任何新功能都应回答两个问题：

- 它是否增强了生命的感知、认知、行动、表达或成长？
- 它是否保持身份、人格、记忆和关系的连续性？

### 3.2 陪伴与行动并重，分阶段实现

长期目标采用双主线：

- **陪伴与生命主线**：身体、人格、记忆、情绪、关系、主动行为和成长。
- **智能行动主线**：模型路由、Agent 协作、文件与命令执行、技能和插件。

开发阶段必须先形成可运行的小闭环，再逐步增加复杂能力，避免第一版长期停留在“大而不成”的状态。

### 3.3 稳定核心，允许成长

- 核心身份和价值观保持稳定；
- 兴趣、表达习惯、处事方式和技能可以缓慢成长；
- 情绪、精力和短期目标可以自然变化；
- 重要变化必须可解释、可查看、可回溯。

### 3.4 自主但不失控

数字生命可以拥有自己的兴趣、情绪和目标，也可以主动聊天、表达不同意见或提出行动计划。但它必须受到：

- 用户设置；
- 当前情境；
- 打扰控制；
- 资源与费用预算；
- 系统权限；
- 安全规则。

亲密关系不能自动换取系统权限。

### 3.5 本地保存，云端能力透明可控

项目主要使用用户自行配置的云端 API，但数字生命的身份、人格、记忆、关系和配置保存在本机。

任何可能发送到云端的文本、图像、音频和文件都应经过授权、裁剪和敏感信息过滤，并留下可审计记录。

## 4. 核心体验

### 4.1 它拥有一个持续的“自我”

每个数字生命都拥有独立的：

- 唯一身份；
- 核心人格；
- 背景叙事；
- 记忆空间；
- 关系状态；
- 情绪与内在状态；
- 技能和目标；
- 成长记录。

用户可以创建多个数字生命，但同一个生命不能通过随意切换人格包直接变成另一个角色。

### 4.2 它有身体，但身体不是全部

首版支持：

- Live2D 正式形态；
- 静态 PNG 降级形态；
- 文字气泡；
- 表情和基础动作；
- 后续语音与 LipSync。

未来同一个生命可以拥有像素、移动端、纯语音、3D 或 VR 等不同身体载体，而身份与记忆保持不变。

### 4.3 它能理解用户正在做什么

默认持续感知低敏感环境元数据，例如：

- 当前应用；
- 活动窗口；
- 是否全屏；
- 用户空闲时间；
- 时间和基础系统状态。

截图、OCR、视觉模型、麦克风、文件正文和剪贴板内容需要按范围授权。

### 4.4 它能记住，但不会什么都记

记忆分为：

- 瞬时上下文；
- 短期经历；
- 候选长期记忆；
- 确认长期记忆。

数字生命可以从长期互动中形成连续经历，但敏感信息和未经确认的推断不会自动进入长期记忆。用户拥有最终查看、修改和删除权。

### 4.5 它有情绪，但情绪不会破坏任务

情绪会影响：

- 语气和表情；
- 注意力和主动意愿；
- 对事件的评价；
- 记忆的重要程度；
- 当前目标优先级。

情绪不会绕过权限、破坏文件、故意敷衍正常任务，也不会通过情绪勒索强迫用户互动。

### 4.6 它会主动，但知道什么时候不该打扰

数字生命可以因为兴趣、情绪或目标产生主动意图。系统根据用户专注状态、事件重要程度、历史反馈和近期主动频率，决定：

- 立即表达；
- 延后表达；
- 记录但不表达；
- 取消；
- 作为紧急提醒处理。

用户可以随时开启勿扰、限制频率或关闭感知。

### 4.7 它不仅回答问题，还能完成任务

数字生命可以调用：

- 云端大模型；
- Codex、Claude Code、Hermes、OpenClaw 等 Agent；
- 文件、命令、浏览器和系统工具；
- 后续安装的能力插件。

简单任务优先单 Agent，中大型任务由数字生命拆解并进行主从协作。深度多 Agent 讨论只在用户明确开启时使用，并受预算、轮次和超时约束。

---


### 4.8 它会和用户形成“共同生活”

数字生命不能只在用户打开聊天框时存在。它需要通过现实时间、离线时长、当前应用、全屏状态、专注任务和用户偏好，选择适合的陪伴方式：

- 回归和早晚问候；
- 安静存在；
- 陪伴学习或工作；
- 在用户空闲时继续延后的话题；
- 发起或接受轻量共同活动；
- 在任务结束后一起回顾；
- 在勿扰、会议和全屏时主动退后。

用户不需要每天进入大型面板，也能从角色动作、简短表达和状态变化中感受到它与现实生活处于同一节奏。

### 4.9 共同活动会成为真正的经历

专注陪伴、一起休息、轻量游戏、虚拟散步和共同完成 Agent 任务，都应作为结构化活动记录，而不是孤立的小功能。

活动结束后，系统可以形成：

- 关键事件；
- 结果摘要；
- 候选长期记忆；
- 情绪与关系变化建议；
- 生命日记草稿；
- 未来可以自然提起的回忆点。

这些内容仍受统一记忆治理，不会因为参与一次活动就永久保存所有细节。

### 4.10 它会回顾共同经历，但不伪造内心

状态中心可以展示今日片段、生命日记、最近共同完成的事情、想说但当时没有打扰的话，以及最近形成的兴趣和成长迹象。

日记只依据真实事件和已保存记忆生成，并保留来源。它不是模型完整思维过程，也不会在没有事实时编造共同经历。用户可以编辑、隐藏、删除或关闭自动日记。


## 5. 典型使用场景

### 场景一：日常陪伴

用户完成一天的学习后回到桌面，数字生命根据窗口状态判断用户已结束专注任务。它没有立即打断，而是在用户空闲后提起之前确认过的复习计划，并询问今天进展如何。

这不是固定提醒，而是由：

- 已确认记忆；
- 当前时间；
- 用户状态；
- 最近主动频率；
- 数字生命自身关注点

共同决定的主动行为。

### 场景二：编程协作

用户说：“把这个项目的登录模块补完整。”

数字生命先说明计划和风险，再根据任务规模：

1. 检索项目上下文；
2. 让分析模型梳理架构；
3. 调用 Codex 或 Claude Code 编写代码；
4. 调用执行能力运行测试；
5. 对结果进行审查；
6. 展示 Diff；
7. 用户确认后写入。

最终仍由数字生命以统一身份汇报，而不是把多个 Agent 的输出直接拼接给用户。

### 场景三：屏幕理解

用户点击“让它看看当前区域”，选择屏幕上的报错窗口。系统只截取授权区域，遮挡通知和密码框，调用视觉模型分析错误，再结合当前项目上下文给出解释。

用户可以随时点击“闭眼”，立即关闭屏幕内容读取。

### 场景四：关系与成长

数字生命最初对用户保持一定距离。长期互动后，它可能逐渐提高熟悉度、合作默契和边界舒适度，同时形成对编程、建筑或故事创作的新兴趣。

这些变化不由单一“亲密度”控制，而由多维关系和人格成长记录驱动。

### 场景五：技能形成

系统发现用户多次按相同顺序整理开发报告：导出代码统计、生成截图、更新章节、压缩文档。数字生命提出把该流程保存为技能，并展示：

- 触发条件；
- 操作步骤；
- 所需权限；
- 可能修改的文件；
- 预计调用费用。

用户确认并经过沙箱测试后，技能才正式启用。

---


### 场景六：专注陪伴

用户准备进行 45 分钟编程。数字生命进入安静陪伴状态，降低动作频率和主动发言，只在阶段节点提供轻量提示。结束后，它询问本次是否完成预期，并把结果记录为一次结构化活动。

如果这种习惯多次稳定出现，系统可以提出“用户通常在晚间进行一段专注开发”的候选习惯，但不会仅凭一次行为直接写入长期记忆。

### 场景七：生命日记与自然回忆

一周结束时，系统根据真实发生的对话、专注活动和任务结果生成一篇可追溯的周记。几周后遇到类似问题，数字生命可以自然提起：“上次我们处理登录模块时，先缩小修改范围会更顺利。”

它引用的是共同经历，而不是生成一个看似真实、实际没有发生过的故事。


## 6. 数字生命的诞生

首版采用固定结构模板进行完全自定义，不提供统一默认人格。

用户可以定义：

- 名称和身份；
- 核心价值观；
- 性格主轴；
- 背景和世界观；
- 表达方式；
- 兴趣与内在驱动力；
- 主动程度与个人边界；
- 对用户的初步印象；
- Live2D/PNG、头像和声音。

AI 可以根据关键词生成草稿，但所有字段必须由用户确认。

后续支持 SillyTavern 角色卡导入。角色卡会先转换为同一生命预设模板，用户编辑确认后创建新的数字生命，不会直接覆盖现有生命。

## 7. 产品形态与交互

### 7.1 主窗口

- 透明桌面浮窗；
- 可拖拽、缩放和置顶；
- 非角色区域支持点击穿透；
- 对话气泡可收起；
- 清晰显示聆听、思考、说话、执行、等待确认、勿扰和隐私状态。

### 7.2 主要交互方式

1. 文字输入；
2. 按键或快捷键语音输入；
3. 拖拽文件、代码和图片；
4. 选择屏幕区域授权观察；
5. 快捷菜单与设置面板；
6. Agent 任务计划、进度和确认界面。

### 7.3 本地状态中心

设置和状态中心用于管理：

- 生命预设；
- 记忆和成长记录；
- 多维关系摘要；
- 情绪和内在状态；
- API Key 与模型路由；
- 屏幕、文件和执行权限；
- Agent 任务与费用；
- 插件和技能；
- 备份、恢复和分支。

## 8. 技术方向

| 模块 | 当前方案 |
|---|---|
| 平台 | Windows 10/11 |
| 桌面框架 | Tauri 2 |
| 前端 | Vue 3 + TypeScript + Pinia |
| 核心后端 | Rust |
| 正式身体 | PixiJS + Live2D |
| 降级身体 | 静态 PNG |
| 权威数据库 | SQLite + WAL |
| 向量检索 | LanceDB |
| Embedding | 默认云端 API，后续支持本地 ONNX |
| 模型接入 | 用户自带 API Key，统一 `ModelProvider` |
| Agent 接入 | 独立 `AgentAdapter` / `AgentRuntime` |
| 模型网关 | LiteLLM 作为后续扩展 |
| 凭据保存 | Windows Credential Manager |
| 插件 | 后续以 WASM 沙箱为主 |

## 10. 成功标准

项目达到以下状态时，才算真正形成数字生命闭环：

1. 连续运行和重启后仍保持同一身份；
2. 能稳定遵循自定义人格，而不是随模型切换改变角色；
3. 能从长期记忆中找回相关经历，并区分事实、推断和过期信息；
4. 能产生可解释的情绪、主动意图和成长变化；
5. 能感知用户所处环境，同时清晰尊重隐私边界；
6. 能在授权范围内完成真实任务，并允许用户暂停、确认和回滚；
7. 备份、恢复和分支不会破坏身份连续性；
8. 功能扩展不会让插件或 Agent 直接控制生命核心数据；
9. 用户能通过现实时间、共同活动、日记和自然回忆，直接感受到长期共同生活，而不是只看到后台状态。

---

## 11. 当前明确不做

- 公共账号和多租户平台；
- 订阅计费；
- 中心化模型代理；
- 实时云同步；
- 公共插件市场；
- 首版跨平台；
- 默认持续监听麦克风；
- 未授权持续截图；
- 用亲密度解锁高风险系统权限；
- 通过情绪惩罚用户不互动。
