# AI数字生命项目—Codex实施路线图

> 版本：2.0  
> 生成日期：2026-07-11  
> 适用基线：`AI数字生命-统一需求基线.md`、`AI桌宠-详细设计说明书_优化版.md`  
> 目标：在 Token / Codex Credits 有限的条件下，以最低返工风险分阶段完成 Windows 本地数字生命工具。

---

## 1. 本版结论

当前文档的小幅修改**不需要推翻 V0.1～V1.0 的总体分级**，但需要修正上一版的模型使用策略：

1. `GPT-5.6 Sol` 只用于架构决策、复杂跨模块问题、安全边界和里程碑审查。
2. `GPT-5.6 Terra` 作为主要实现模型，承担大部分 Rust / TypeScript 集成开发。
3. `GPT-5.6 Luna` 承担结构明确、可验收、重复性高的任务。
4. 不再用 API 单价直接推算 Codex Credits；以 Codex 官方本地任务参考为准：Sol 约 14、Terra 约 7、Luna 约 3 credits/消息，实际会随上下文、工具调用和任务复杂度变化。
5. LiteLLM 不进入首版；SQLite + LanceDB 保持 V0.2 核心能力；云同步继续排除。
6. 酒馆角色卡导入保持 V0.3，不提前进入 V0.1。
7. 多 Agent、技能学习、WASM 插件严格按 V0.5、V0.6 实现，不在早期预埋过度抽象。

---

## 2. 三个模型的固定职责

| 模型 | 适合任务 | 不适合浪费在 | 推荐 effort |
|---|---|---|---|
| `gpt-5.6-sol` | 架构、模糊需求、跨模块设计、并发/一致性、安全审查、复杂故障、最终验收 | 目录创建、DTO、普通 CRUD、格式化、批量测试 | Medium 做规划；High 做核心设计；Max 仅用于极难故障或最终安全审查 |
| `gpt-5.6-terra` | 日常主体实现、Rust/TS 集成、Tauri、Live2D、LanceDB、语音、Agent Adapter、调试 | 大量机械复制、简单文档同步 | Medium 默认；High 用于复杂集成和难调试问题 |
| `gpt-5.6-luna` | 脚手架、类型、migration、简单 CRUD、测试样例、批量重命名、文档、样板适配器 | 核心架构、权限模型、数据一致性算法 | Low 默认；Medium 用于测试和中等复杂度转换 |

### 2.1 推荐任务数量分配

- Luna：约 55%
- Terra：约 37%
- Sol：约 8%

按官方本地任务参考 credits 粗略折算，实际消耗大约会落在：

- Luna：约 30%
- Terra：约 48%
- Sol：约 22%

这比上一版更省预算，同时保留关键架构质量。

### 2.2 固定协作模式

```text
Sol：确定边界和验收标准
  ↓
Terra：实现主功能并解决集成问题
  ↓
Luna：补测试、迁移、文档和重复代码
  ↓
Terra：修复测试与整合
  ↓
Sol：只做阶段性审查，不重新实现
```

## 3. Codex 会话规则

每个 Codex 会话只处理一个独立任务，满足以下要求：

1. 修改范围明确，最好控制在一个模块或一个垂直功能。
2. 开始前必须存在 Git checkpoint。
3. 提示词包含：目标、允许修改范围、禁止事项、验收标准、测试命令。
4. 任务结束必须输出：修改文件、执行命令、测试结果、遗留问题。
5. 不允许“顺手重构”无关模块。
6. 不让一个会话跨越两个版本阶段。
7. 复杂任务先让 Sol 输出计划或 ADR，再开新 Terra 会话实现。
8. Luna 只在已有明确接口和范例后工作。
9. 每完成一个可独立验收任务就提交一次 Git commit。
10. 根目录 `AGENTS.md` 控制在约 150～250 行；模块特殊规则放到嵌套 `AGENTS.md`。

通用尾部约束：

```text
只完成本任务验收范围。
不要重构无关模块，不新增未批准依赖，不修改冻结需求文档。
完成后运行相关测试，列出修改文件、命令、测试结果和遗留风险，然后停止。
```

# 14. Token / Credits 节省策略

1. **先搜索，后实现**：让 Luna 先定位文件和列出相关代码，Terra 只读必要上下文。
2. **提示词引用路径，不粘贴整份文档**：Codex 直接读取仓库内文档。
3. **冻结接口后再批量施工**：先用 Sol/Terra 确定接口，再让 Luna 生成相似实现。
4. **不在同一会话中反复改方向**：需求变化就结束当前任务，新开计划任务。
5. **保留上下文只用于同一任务**：跨任务新开会话，避免旧上下文干扰。
6. **测试失败交给 Terra，不让 Sol 做普通编译修复**。
7. **Sol 审查以 diff/commit 为输入，不让它重新遍历全部仓库**。
8. **Max 只用于 V0.4/V1.0 安全门禁或真正阻塞的复杂故障**。
9. **Ultra 不用于日常编码**；只有任务可拆成多个独立审查流时才启用。
10. **定期压缩 AGENTS.md**，删除已经失效的临时规则。
11. **每个任务限定最大修改文件数**；超过范围先停下重新规划。
12. **优先复用现有模式**，不要让模型为相似模块重新设计架构。

# 15. 当前文档修改对任务分级的影响

| 文档决策 | 路线影响 | 本版处理 |
|---|---|---|
| 本地个人工具，不是平台 | 降低早期复杂度 | 删除账号、订阅、多租户和中心服务任务 |
| 云端 API 为主 | V0.1 必须有 Provider 与凭据 | 提前 ModelProvider 和 Credential Manager |
| SQLite + LanceDB | V0.2 为高风险核心 | 保留独立 Spike 和一致性 ADR |
| 完全自定义生命模板 | V0.1 数据结构更重要 | 提前人格分层、版本和冲突检查 |
| 酒馆角色卡导入 | 不影响 V0.1 | 保持 V0.3，转换为草稿 |
| LiteLLM 后续扩展 | 减少早期进程与部署 | 不进入 V0.1～V0.2 硬依赖 |
| 多 Agent 主从协作 | 必须建立在安全 Agent Runtime 上 | 保持 V0.5，不提前 |
| 插件不可改核心数据 | 插件 API 必须后抽取 | 保持 V0.6，先用内置模块验证 |
| 不做云同步 | 取消服务器和冲突合并 | 仅保留本地快照和加密档案 |

结论：**版本分级本身不变，主要变化是更严格地限制 Sol 使用、把更多明确任务下放给 Luna，并将高风险原型放在正式开发之前。**
