## 1. 审查结论

原文档具有较丰富的功能设计和实现细节，但存在三个系统性问题：

1. **产品本体不清晰**：数字生命、AI 桌宠、多模型路由和 Agent 平台混为同一层级。
2. **版本范围失控**：大量功能同时标为 V1/P0，导致优先级失效。
3. **架构概念混用**：模型 Provider、Agent Runtime、工具执行、插件和人格系统边界不清。

本轮优化已建立统一需求基线，并重写五份文档的关键结构。优化后的核心定位为：

> 本项目是 Windows 本地个人数字生命工具。身份、人格、记忆、关系和生命连续性由本地核心维护；云端模型、Agent、工具和插件只提供能力。

## 2.1 本轮共同生活体验增强

上一版本已经解决“数字生命是什么”和“核心数据如何管理”，但仍存在一个产品层缺口：人格、记忆、情绪、关系和感知大多停留在后台机制，用户未必能在每天使用中直接感受到连续生活。

本轮新增：

| 编号 | 原缺口 | 处理结果 |
|---|---|---|
| E-01 | 缺少每天可重复的陪伴闭环 | 增加现实时间、回归问候、安静存在和专注陪伴 |
| E-02 | 记忆与关系缺少前台载体 | 增加生活事件、生命日记、自然回忆和关系里程碑 |
| E-03 | 小游戏或场景容易成为孤立功能 | 定义统一 `ActivitySession`，活动必须产出结构化经历 |
| E-04 | 人格成长用户不可感知 | 通过称呼、主动方式、兴趣、合作习惯和成长摘要展示 |
| E-05 | 现实时间可能导致频繁模型调用 | 明确事件驱动、本地规则优先和低频批量总结 |
| E-06 | 多入口可能形成多个角色实例 | 明确桌宠、状态中心、语音、活动和 Agent 共享同一 `life_id` |
| E-07 | 日记可能伪造“内心”或共同经历 | 要求来源引用、不足则不生成、禁止保存完整推理过程 |
| E-08 | 关系玩法可能变成刷好感度 | 保留多维关系，禁止离线惩罚、付费绑定和情绪压力 |

新增独立设计文档：《AI数字生命—共同生活与陪伴体验系统设计》。

## 4. 优化后仍存在的风险

## 4.1 必须优先验证

### C-01：Live2D 技术栈版本风险

`pixi-live2d-display`、PixiJS 和 Cubism Core 的版本组合必须通过原型锁定。文档不应在未验证前宣称某个版本“官方支持”或直接可用。

**动作**：V0.1 开发前先完成加载、动作、LipSync、资源释放和透明窗口原型。

### C-02：LanceDB 与桌面打包风险

采用 LanceDB 的方向合理，但 Rust API、Windows 打包、索引目录迁移和大规模写入性能需要验证。

**动作**：建立测试程序，覆盖写入、删除、过滤、重建和模型维度切换。

### C-03：Agent 工具权限风险

Agent Runtime 如果直接继承用户终端权限，可能绕过应用确认界面。

**动作**：所有 Agent 工具能力必须经过 Tool Broker；无法拦截的 CLI Agent 应限制到隔离工作目录，并在首版禁用高风险系统工具。

### C-04：模型人格一致性风险

不同模型在风格、拒绝方式和指令遵循上差异明显。

**动作**：建立人格一致性回归集，在每个 Provider 上测试身份、自称、价值观、语气和记忆引用。


### C-05：共同生活内容真实性风险

日记、回忆和关系变化如果缺少来源约束，容易产生“明明没有发生过却被写成共同经历”的问题。

**动作**：所有日记和里程碑保存事件或记忆引用；无足够事实时不生成；删除来源时同步标记派生内容。

### C-06：陪伴功能造成打扰和成本膨胀

现实时间、窗口变化和主动行为如果每次都调用模型，会带来频繁打扰、Token 消耗和待机资源增长。

**动作**：模式判断、动作、计时和固定提示本地执行；模型只用于低频摘要和高价值表达；活动模板声明预算上限。


## 4.2 中等优先级风险

| 编号 | 风险 | 建议 |
|---|---|---|
| M-01 | 文档仍然较大 | 实施时拆出 API、数据库和插件规范为独立契约 |
| M-02 | 生命模板字段可能过多 | 前端提供基础/高级模式，底层结构保持统一 |
| M-03 | 关系维度更新易过拟合 | 限制单次变化并要求长期证据 |
| M-04 | 情绪状态会污染任务 | 任务执行设置最低质量和安全约束 |
| M-05 | 候选记忆过多 | 设定批处理、过期和用户确认队列 |
| M-06 | 云端 Embedding 持续产生费用 | 批量、缓存、去重，并支持后续本地 ONNX |
| M-07 | 备份体积增长 | LanceDB 默认不打包，资源支持引用或可选打包 |
| M-08 | 插件系统过早抽象 | V0.x 先以内置模块验证，再在 V0.6 抽 Capability API |

- [ ] Tauri 透明窗口和点击穿透；
- [ ] Live2D/PNG 切换和资源释放；
- [ ] 云端 API 流式输出；
- [ ] Windows Credential Manager；
- [ ] SQLite migration；
- [ ] LanceDB Rust 写入、过滤、删除和重建；
- [ ] 一个 Agent CLI 的创建、流式、取消和工作目录；
- [ ] 本地快照和加密档案原型；
- [ ] 现实时间、陪伴模式和专注活动原型；
- [ ] 生活事件聚合与日记来源追踪原型。

### 架构守则

- [ ] 模型 Adapter 不持有生命身份；
- [ ] Agent 不直接写核心数据库；
- [ ] Tool Broker 是所有执行入口；
- [ ] SQLite 是记忆权威数据；
- [ ] 插件只提交状态变化建议；
- [ ] 关系状态不参与权限提升；
- [ ] 高敏感感知有明确状态提示和停止按钮；
- [ ] API Key 不进入日志、配置和备份。

### V0.1 验收

- [ ] 创建自定义数字生命；
- [ ] 重启后身份、人格和对话保持；
- [ ] 更换模型后角色核心行为不突变；
- [ ] Live2D 失败时自动降级 PNG；
- [ ] API Key 可安全写入、读取、轮换和删除；
- [ ] 本地快照可恢复；
- [ ] 24 小时运行无明显内存泄漏；
- [ ] 全屏和勿扰状态下不产生低优先级打扰；
- [ ] 专注陪伴完成后形成结构化事件；
- [ ] 基础共同生活循环不依赖持续模型调用。

## 8. 最终结论

优化后的文档已经解决了原方案最关键的定位和边界问题，可以作为项目开发的统一架构基线。

目前不应继续扩充更多功能清单，而应进入原型验证和 V0.1 实现。最优先验证的四个技术点是：

1. Tauri + Live2D/PNG 桌面身体；
2. 生命人格与模型切换解耦；
3. SQLite + LanceDB 记忆架构；
4. Agent Runtime + Tool Broker 的权限边界；
5. 现实时间、生活事件、专注陪伴和日记来源追踪构成的最小共同生活闭环。

在这四项没有通过原型前，不建议提前投入完整插件系统、全双工语音或复杂多 Agent 团队。
